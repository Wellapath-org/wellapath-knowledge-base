# CANDIDATE — NOT PUBLISHED, NOT APPROVED

Everything in this directory is an **unapproved release candidate**. Nothing here
is served by any endpoint, referenced by any manifest, or uploaded to R2.

---

## Why this directory exists

Published artifacts live at the repository root. That is the directory the data
engineer uploads to R2 from, and per
`wellapath-backend/docs/ARTIFACT_RELEASE_PROCESS.md` an artifact version is
immutable once published.

Putting an unapproved candidate at the root would make it structurally
indistinguishable from a published artifact — one careless upload away from
shipping something no clinician has reviewed. The candidate keeps the
conventional filename and lives here instead, so its status is visible from the
path alone.

`tools/check_compatibility.py` asserts that `token_dictionary.ng.v2.0.json` does
**not** exist at the repository root while the candidate is unapproved.

## Do not

- Do not upload anything in this directory to R2.
- Do not wire `manifest.candidate.json` into `wellapath-backend/src/routes/config.ts`.
- Do not move `token_dictionary.ng.v2.0.json` to the repository root.
- Do not hand-edit the artifact. Change the generator and rebuild, or the
  reproducibility check fails.
- Do not set `clinical_review.status` to `reviewed` without a named reviewer, a
  date and a resolvable evidence link. The validator rejects a review claim with
  no evidence, and so should any reviewer.

---

## When approval arrives

1. Record clinical review in `_metadata.clinical_review` (reviewer, date,
   evidence link) via the generator.
2. Set `release_status` to `approved_unpublished` and set `release_date`.
3. Rebuild, re-run `python3 tools/run_w2_checks.py`, record the new SHA256.
4. Move the artifact to the repository root.
5. Follow `wellapath-backend/docs/ARTIFACT_RELEASE_PROCESS.md` from the upload
   step onward. The backend engineer recomputes the hash independently.

Rollback procedure: `docs/VOCABULARY_ROLLBACK.md`.
